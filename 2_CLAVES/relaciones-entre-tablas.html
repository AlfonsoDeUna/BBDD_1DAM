Conectar tablas: 1:N, N:M y 1:1

La FK va en el lado N. El 1 se repite en pedidos: Ana puede tener varios pedidos, cada uno con su propia PK.

Primero, el padre

CREATE TABLE clientes (
    id_cliente INT PRIMARY KEY,
    nombre VARCHAR(100) NOT NULL
);

Después, la hija

CREATE TABLE pedidos (
    id_pedido INT PRIMARY KEY,
    id_cliente INT NOT NULL,
    CONSTRAINT fk_pedidos_cliente
        FOREIGN KEY (id_cliente)
        REFERENCES clientes(id_cliente)
        ON DELETE RESTRICT
        ON UPDATE CASCADE
);

¿Dónde guardarías quién está en cada curso?

Si ponemos un único id_curso en alumnos, solo cabe un curso por alumno. Si ponemos un único id_alumno en cursos, solo cabe un alumno por curso. ¿Qué tabla nos falta?

La solución: una tabla intermedia

Creamos matriculas. Cada fila conecta un alumno con un curso. La relación N:M se transforma en dos relaciones 1:N.

Dos FK y una PK compuesta. Cada identificador puede repetirse, pero la pareja alumno + curso no. Evitamos matricular dos veces al mismo alumno en el mismo curso.

1 · Crear las dos tablas de origen

CREATE TABLE alumnos (
    id_alumno INT PRIMARY KEY,
    nombre VARCHAR(100) NOT NULL
);

CREATE TABLE cursos (
    id_curso INT PRIMARY KEY,
    titulo VARCHAR(100) NOT NULL
);

2 · Crear la tabla intermedia

CREATE TABLE matriculas (
    id_alumno INT NOT NULL,
    id_curso INT NOT NULL,
    PRIMARY KEY (id_alumno, id_curso),
    CONSTRAINT fk_matriculas_alumno
        FOREIGN KEY (id_alumno)
        REFERENCES alumnos(id_alumno)
        ON DELETE CASCADE ON UPDATE CASCADE,
    CONSTRAINT fk_matriculas_curso
        FOREIGN KEY (id_curso)
        REFERENCES cursos(id_curso)
        ON DELETE CASCADE ON UPDATE CASCADE
);

Si borramos un alumno, CASCADE borra sus matrículas, no los cursos. Si borramos un curso, se borran sus matrículas, no los alumnos.

¿Cómo se ven estas matrículas con INSERT?
INSERT INTO alumnos VALUES (1, 'Ana'), (2, 'Mario');
INSERT INTO cursos VALUES (10, 'MySQL'), (20, 'HTML');
INSERT INTO matriculas VALUES (1, 10), (1, 20), (2, 10);

Volver a insertar (1, 10) sería rechazado: esa pareja ya existe.

FK + UNIQUE = como máximo un perfil por usuario. La FK exige que el usuario exista; UNIQUE impide repetirlo en perfiles. NOT NULL exige que cada perfil tenga usuario.

Lucía todavía no tiene perfil. Estas restricciones permiten cero o un perfil por usuario; no obligan a crear un perfil para cada usuario. Por eso el esquema indica 0..1.

1 · La tabla de usuarios

CREATE TABLE usuarios (
    id_usuario INT PRIMARY KEY,
    nombre VARCHAR(100) NOT NULL
);

2 · La FK no puede repetirse

CREATE TABLE perfiles (
    id_perfil INT PRIMARY KEY,
    id_usuario INT NOT NULL,
    biografia VARCHAR(200),
    CONSTRAINT uq_perfil_usuario
        UNIQUE (id_usuario),
    CONSTRAINT fk_perfil_usuario
        FOREIGN KEY (id_usuario)
        REFERENCES usuarios(id_usuario)
        ON DELETE CASCADE
        ON UPDATE CASCADE
);
Otra forma: compartir la clave primaria

Podemos prescindir de id_perfil y usar id_usuario como PK y FK a la vez.

CREATE TABLE perfiles (
    id_usuario INT PRIMARY KEY,
    biografia VARCHAR(200),
    FOREIGN KEY (id_usuario)
        REFERENCES usuarios(id_usuario)
        ON DELETE CASCADE ON UPDATE CASCADE
);

Es una alternativa a la tabla perfiles anterior. La PK ya impide duplicar id_usuario.

¿Qué construye cada relación?

  • 1:N: la FK está en el lado N y puede repetirse.
  • N:M: una tabla intermedia con dos FK; la pareja es única.
  • 1:1: la FK no puede repetirse: lleva UNIQUE o es también la PK.

Ejemplos independientes, con tablas InnoDB. Referencia: Manual de MySQL · Claves foráneas.
