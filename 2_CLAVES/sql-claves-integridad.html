De las reglas a las tablas

Ahora sí: todo en SQL

Creamos las tablas de una aplicación web de pedidos: clientes, pedidos y sus líneas.

Primero, la sintaxis de referencia

1 · PRIMARY KEY en columna

columna tipo_dato [AUTO_INCREMENT]
    PRIMARY KEY

Para una PK de una sola columna. AUTO_INCREMENT es opcional y se usa con un tipo numérico entero.

2 · PRIMARY KEY de tabla

[CONSTRAINT nombre_pk]
PRIMARY KEY (columna1 [, columna2, ...])

Sirve para claves simples o compuestas. Se escribe como un elemento más dentro de CREATE TABLE.

3 · FOREIGN KEY de tabla

[CONSTRAINT nombre_fk]
FOREIGN KEY (columna_hija)
    REFERENCES tabla_padre(columna_padre)
    [ON DELETE accion]
    [ON UPDATE accion]

CONSTRAINT permite nombrar la FK. Las acciones de borrado y actualización se eligen por separado.

4 · Añadir una FK después

ALTER TABLE tabla_hija
ADD [CONSTRAINT nombre_fk]
FOREIGN KEY (columna_hija)
    REFERENCES tabla_padre(columna_padre)
    [ON DELETE accion]
    [ON UPDATE accion];

La columna hija y la tabla padre ya deben existir.

Los corchetes indican partes opcionales: no se escriben. Sustituye los nombres genéricos por los de tus tablas y columnas.

¿Todo en una columna? En MySQL podemos declarar la PK junto a la columna. Para crear una FK efectiva con InnoDB, usamos la cláusula de tabla FOREIGN KEY (...) REFERENCES ...; no basta con escribir REFERENCES junto al tipo de una columna.

1 · Tabla padre: clientes

CREATE TABLE clientes (
    id_cliente INT AUTO_INCREMENT
        PRIMARY KEY,
    nombre VARCHAR(100) NOT NULL
);

MySQL genera id_cliente. PRIMARY KEY garantiza que sea único y no nulo.

2 · Tabla hija: pedidos

CREATE TABLE pedidos (
    id_pedido INT AUTO_INCREMENT
        PRIMARY KEY,
    fecha DATE NOT NULL,
    id_cliente INT NOT NULL,
    FOREIGN KEY (id_cliente)
        REFERENCES clientes(id_cliente)
        ON DELETE RESTRICT
        ON UPDATE CASCADE
);

No permite borrar un cliente con pedidos. Si cambia su ID, las FK de sus pedidos se actualizan.

Forma B · Alternativa a la A

Las restricciones, con CONSTRAINT

Mismas tablas y mismas reglas, pero declarando la PK al final y dando un nombre explícito a la FK. Usa la forma A o la B; no ejecutes ambas sobre las mismas tablas.

clientes

PKid_clienteINT · AUTO_INCREMENT
nombreVARCHAR(100)
CONSTRAINT pk_clientes → PRIMARY KEY
1N

pedidos

PKid_pedidoINT · AUTO_INCREMENT
fechaDATE
FKid_clienteINT · NOT NULL
CONSTRAINT fk_pedidos_clientes → FOREIGN KEY

Forma B: la misma relación, declarando las restricciones por separado. En MySQL, la PK se llama PRIMARY.

1 · PK como restricción de tabla

CREATE TABLE clientes (
    id_cliente INT NOT NULL AUTO_INCREMENT,
    nombre VARCHAR(100) NOT NULL,
    CONSTRAINT pk_clientes
        PRIMARY KEY (id_cliente)
);

Aunque escribamos pk_clientes, en MySQL el nombre efectivo de la PK es siempre PRIMARY.

2 · PK y FK como restricciones

CREATE TABLE pedidos (
    id_pedido INT NOT NULL AUTO_INCREMENT,
    fecha DATE NOT NULL,
    id_cliente INT NOT NULL,
    CONSTRAINT pk_pedidos
        PRIMARY KEY (id_pedido),
    CONSTRAINT fk_pedidos_clientes
        FOREIGN KEY (id_cliente)
        REFERENCES clientes(id_cliente)
        ON DELETE RESTRICT
        ON UPDATE CASCADE
);

fk_pedidos_clientes identifica la restricción que conecta pedidos con clientes.

ON DELETE SET NULL: se borra el cliente y se conserva el pedido con su FK a NULL.

Ejemplo: conservar el pedido sin cliente

Alternativa a la tabla pedidos anterior.

CREATE TABLE pedidos (
    id_pedido INT AUTO_INCREMENT PRIMARY KEY,
    fecha DATE NOT NULL,
    id_cliente INT NULL,
    CONSTRAINT fk_pedidos_clientes
        FOREIGN KEY (id_cliente)
        REFERENCES clientes(id_cliente)
        ON DELETE SET NULL
        ON UPDATE CASCADE
);

Al borrar al cliente, el pedido permanece con id_cliente = NULL. Por eso esa columna no puede ser NOT NULL.

Con InnoDB, NO ACTION equivale a RESTRICT. Si omites una acción, se aplica NO ACTION. SET DEFAULT no está admitido.

Crear líneas de pedido

CREATE TABLE lineas_pedido (
    id_pedido INT NOT NULL,
    num_linea INT NOT NULL,
    descripcion VARCHAR(100),
    CONSTRAINT pk_lineas_pedido
        PRIMARY KEY (id_pedido, num_linea),
    CONSTRAINT fk_lineas_pedido
        FOREIGN KEY (id_pedido)
        REFERENCES pedidos(id_pedido)
        ON DELETE CASCADE
        ON UPDATE CASCADE
);

Aquí la PK tiene dos columnas y la FK, una. Si se borra un pedido, se borran sus líneas.

Si una FK referencia una PK compuesta

Fragmento de otra tabla que necesite apuntar a una línea concreta.

num_linea INT NOT NULL,
CONSTRAINT fk_linea_referenciada
    FOREIGN KEY (id_pedido, num_linea)
    REFERENCES lineas_pedido

    ON UPDATE CASCADE

Cuando la tabla ya existe

Añadir la FK con ALTER TABLE

Este ejemplo supone que pedidos ya tiene id_cliente, pero todavía no tiene la restricción FK.

1N

PKid_pedidoINT
FKid_clienteINT
ALTER TABLE añade la restricción FK

ALTER TABLE: la columna ya existía; ahora declaramos la regla que protege la relación.

ALTER TABLE pedidos
ADD CONSTRAINT fk_pedidos_clientes
    FOREIGN KEY (id_cliente)
    REFERENCES clientes(id_cliente)
    ON DELETE RESTRICT
    ON UPDATE CASCADE;

Los datos existentes deben cumplir la relación. Si un pedido apunta a un cliente que no existe, hay que corregirlo antes de añadir la FK.

Antes de escribir: crea primero el padre; usa tipos compatibles —por ejemplo, INT con INT y el mismo signo—; decide si la FK admite NULL y elige ON DELETE y ON UPDATE por separado. Para una clave compuesta, respeta el número y orden de las columnas.
